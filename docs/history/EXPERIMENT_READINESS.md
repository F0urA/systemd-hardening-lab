## Статическая проверка

На переданной удалённой копии выполнено:

- `bash -n` для всех 15 файлов `.sh` — все успешно разобраны, код завершения 0.
- `ast.parse` для всех 14 файлов `.py` в `scripts_v005` и `stand_v005/probes` — все успешно разобраны, код завершения 0.

Проверка не импортировала и не запускала исследуемые Python-модули, не выполняла Bash-сценарии, не создавала Python bytecode и не меняла службы. Это подтверждает синтаксис, но не исправность во время исполнения и не соответствие научному протоколу. PowerShell-сценарий и C-исходники прочитаны как материалы; их исполнение/компиляция в этой передаче не выполнялись.

## Состояние существующей ВМ при чтении

ВМ имеет 4 vCPU и около 4 ГБ RAM; systemd 257. Свободно около 28 ГБ на разделе с `/root` и `/var`. Основные зависимости, включая `strace`, уже установлены; Git отсутствует. Устанавливать их заново через архивный сборщик не требуется.

- `slab-nginx`, `slab-redis`, `slab-postgresql` и четыре `lab-proc-target@...` находятся в состоянии `inactive`. Основные службы disabled; их запуск и включение на загрузке — разные действия, включение для опытов не обязательно.
- Unit-файлы и конфигурации Nginx/Redis семантически соответствуют комплекту v005; отличающиеся SHA256 объясняются видимыми комментариями/форматированием. Окончательную сверку всех значимых настроек выполнить перед подготовкой стенда.
- Архивные P1/P2 Nginx, `isolation_probe.py` и `extended_probe.py` совпадают с установленными файлами байт-в-байт.
- Действующие P4 содержат ожидаемые директивы, но имеют иной текст/комментарии; их нельзя молча заменять ради совпадения хешей. Каждый будущий скрипт требует совпадения действующего `90-hardening.conf` именно с сохранённым P4 этой ВМ.
- В каталогах drop-in обнаружены только `90-hardening.conf`.
- Три помощника под именами v005 (`slab_fp_v005.sh`, `slab_inservice_v005.sh`, `slab_dropuser_v005.py`) отсутствуют в `/usr/local/bin`.
- Отсутствуют `/tmp/systemd-lab-marker`, `/dev/systemd-lab-null` и `slab-volatile.service`. Эти тестовые объекты необходимо восстанавливать после загрузки до микропроб; иначе отсутствие объекта может ошибочно учитываться как защитное блокирование.
- `uid-helper` уже установлен с режимом 4755, `lab-target` — 0755. Их наличие и назначение следует учитывать; пересборка установщиком сейчас не выполнялась.
- Порты стенда 808, 6380, 55432 не слушают. Есть иные службы ВМ; их назначение следует учесть при будущей фиксации фоновой нагрузки.
- Гость сообщает AMD Ryzen 5 2600; чтение `Win32_Processor` на Windows-хосте также подтвердило AMD Ryzen 5 2600, 6 физических / 12 логических ядер. Старые протоколы описывают Intel Core Ultra. Применять архивную маску Intel `0x3C03` на этой машине нельзя. Для данного негибридного процессора требуется отдельная запись фактических условий.
- Часовой пояс гостя `+01:00`, пользовательский — Москва `+03:00`. В новых журналах использовать UTC либо ISO-время с явным offset и зафиксировать разницу часов, прежде чем связывать данные гостя с журналом Windows.
- `apt-cache policy` показывает первую доступную новую службу memcached 1.6.42-alt1; memcached/unbound/mosquitto ещё не установлены. По замороженному порядку проверки шаг 26 должен выбрать memcached, если доступность пакета подтвердится при подготовке.

## Исправления и решения до будущих измерений

Изложенные ниже изменения **не внесены**. Они должны быть оформлены в рабочей копии и зафиксированы до соответствующих измерений; значимые расхождения протокола разрешаются явно, а не задним числом по результатам.

| Проблема | Конкретное место | Необходимое действие |
|---|---|---|
| Обязательный расширенный контракт не участвует в F | `build_criteria_v005.py`, строки 137 и 174: чтение только `candidates.csv`; `functional_ext_v005.sh` создаёт `contract.csv` | Добавить явный источник обязательного контракта, исключать кандидата при любом его FAIL; отсутствие обязательной проверки не считать PASS |
| Новые ступени Redis/PostgreSQL не проверяются расширенным контрактом | `functional_ext_v005.sh`, строка 182: жёсткое `P0 P4 P6` | Параметризовать список кандидатов и включить P1/P2/P1d, сохранив исходы всех кандидатов |
| Ненасыщенная серия шага 25 не реализована | `benchmark_v005.sh`, строки 144–145: оба генератора `-c 25`; переменная `NGINX_C` отсутствует | Реализовать документированный параметр соединений, сохранять его в platform.txt, выполнить отдельный пилот и закрепить значение перед серией |
| Возможная unset-переменная при построении абляций | `cap_ablation_v005.sh`, строка 30: `local name=... new="$DIR/$name.conf"` одной строкой | Разделить объявление локальных переменных и вычисление зависимого пути; `bash -n` этот риск не обнаруживает |
| Ошибка/пустой ответ может трактоваться как BLOCKED | `scenarios_v005.sh`, строки 264 и 298, аналогичные ветви | Требовать явный достоверный статус и/или подтверждение результата; ошибки запуска и неожиданное отсутствие ответа фиксировать как ERROR/UNEXPECTED и исключать из доказательства защиты |
| Не реализована часть функциональных обещаний протокола | `protocol_review2_v005.txt`, раздел 5, и `functional_ext_v005.sh` | Отдельно выполнить/реализовать TLS + локальный upstream и согласовать покрытие миграции после reload/restart/crash; сейчас есть только миграция после reopen |
| Defaults нагрузки Redis не соответствуют замороженным параметрам | `benchmark_v005.sh`, defaults 100000 запросов/2 потока; `protocol_load_v005.txt` требует 3000000/3 | Будущие серии запускать с явными `REDIS_N=3000000 REDIS_THREADS=3` и записывать параметры |
| Новые ступени не входят в defaults сценариев и микропроб | `scenarios_v005.sh` и `probe_all_v005.sh` | Для Redis/PG задать P0/P1/P2/P1d/P4/P6, для микропроб включить P1d; заново собрать данные всех этих ступеней |
| Число сравнений в примере GUIDE неверно для новых лестниц | R2/R3 имеют 5 ограниченных кандидатов P1/P2/P1d/P4/P6, пример показывает family=4 | До анализа зафиксировать число кандидатов и использовать M=5 для полной этой семьи; Nginx R1 имеет M=4 |
| Нет реализации шага 26 | `procedure_v005.txt`, раздел применения к новой службе | Подготовить unit, конфигурацию, нагрузку, обязательный контракт, цели, ячейки и план измерений memcached заранее; не менять их после просмотра результатов |

Дополнительные протокольные ограничения:

- GUIDE ошибочно описывает шаг 25 как не меняющий службы: benchmark переключает профили и затем восстанавливает P4.
- Правило вывода целей формулирует чтение записываемого службой пути, но Nginx G4 в отдельном протоколе/скрипте определён как запись в каталог журналов. Это содержательное расхождение нужно описать и разрешить до новых проверок; нельзя утверждать без оговорки, что все цели механически выведены одним правилом.
- У обычного memcached немного постоянных файловых путей. Цели шага 26 надо выводить из фактического unit/config; искусственные файловые цели нельзя выдавать за естественные свойства службы. Допустим любой заранее предусмотренный исход, включая отсутствие допустимого кандидата или отсутствие различия правил.
- Требование архива публиковать протокол в GitHub до опытов в этой передаче не выполнено и публикация запрещена. Локальный датированный snapshot/manifest обеспечит внутреннюю прослеживаемость, но не равноценен независимой публичной preregistration. Это нужно прямо указать в будущем отчёте.
- После USR1 Nginx может передать журнал `labweb`, и последующий restart профиля без CAP_DAC_OVERRIDE может не пройти. Это **предположение, ещё не измеренный исход нового этапа**. Не вставлять скрытый `chown` между обязательными операциями, чтобы получить PASS. Явный возврат владельца журнала root проверяется отдельно как шаг миграции.

## Конкретный порядок будущей работы

Перед запуском агент должен прочитать `HANDOFF_v005.md`, `GUIDE_v005.md`, `procedure_v005.txt`, `protocol_review2_v005.txt` и `protocol_load_v005.txt`. Правки исследовательской процедуры и полноразмерные серии не входят в завершённую здесь передачу файлов.

1. Сохранить состояние существующих unit/config/profile/helper и применить проверенные необходимые исправления рабочей копии. Не выполнять архивный `setup_stand_v005.sh`: существующий стенд нужно дооснастить точечно.
2. Восстановить летучие тестовые объекты, установить отсутствующие помощники под именами v005, запустить три лабораторные службы и четыре процесса-мишени. Проверить отсутствие посторонних drop-in и идентичность действующего P4 сохранённому P4 этой ВМ.
3. Проверить GET/PING/SELECT, конфигурацию PostgreSQL и наличие `systemd_bench`; сверить владельцев и режимы файлов. Построить отсутствующие P6/P1r/P1c и Redis/PG P1/P2/P1d, не заменяя существующие отличающиеся профили молча.
4. Зафиксировать UTC-время, параметры машины и фоновых служб, протокол, SHA256 сценариев/конфигураций/профилей до измерений. Убедиться, что журнал Windows содержит действительные данные; его англоязычные performance counter paths могут потребовать адаптации к языку Windows.
5. Начать с **шага 22**: расширенный функциональный контракт Nginx и миграция P0/P1→P1c. Проверить договор Redis/PG для новых ступеней, а не только доступность.
6. **Шаг 19**: `PROFILES='P1 P1r P1c' ./context_compare_v005.sh`. Сопоставить credentials/capabilities/seccomp/namespaces/mounts и все статусы микропроб; отсутствие in-service данных нельзя считать совпадением.
7. **Шаг 20**: построить capability-варианты, затем запустить сценарии с P0-контролем и P1r/P1c/P1cADMIN/P1cPTRACE/P1cDAC/P1cCHROOT. Наличие P0 нужно для подтверждения достижимости целей до ограничений.
8. **Шаг 21**: полные сценарии Nginx плюс Redis/PG P0/P1/P2/P1d/P4/P6; сохранить реальные ошибки/UNEXPECTED, проверить покрытие объявленных обходов. Унаследованный дескриптор до применения профиля не реализован текущим transient helper; границы утверждения нужно сузить либо заранее реализовать отдельный сценарий.
9. Заново выполнить микропробы для используемых кандидатов, включая P1d. Старые metrics не подставлять в таблицы новой ВМ.
10. До нагрузочных серий выполнить пилот Nginx из 10 блоков. Условие протокола: CV P0 ≤5%; для насыщенного режима проверить CPU службы >90%. Не применять параметры affinity исходного Intel-хоста к AMD.
11. **Шаг 23 / R1**: Nginx, 60 рандомизированных блоков P0/P1c/P4/P5/P6; явно NGINX_N=100000, KEEPALIVE=0, PIN=1, STALL_MS=500.
12. **Шаг 24 / R2/R3**: Redis 20 блоков P0/P1/P2/P1d/P4/P6 с REDIS_N=3000000 и REDIS_THREADS=3; PostgreSQL 10 таких блоков, PG_T=60.
13. **Шаг 25 / R4**: после реализации параметра нагрузки пилотировать устойчивые CPU 40–70%, зафиксировать NGINX_C и затем выполнить 60 блоков P0/P1c/P4. Если диапазон не достигается, сохранить failed-результат и назвать ограничение.
14. **Шаг 26**: подготовить и заранее зафиксировать применение неизменной процедуры к memcached; выполнить один запланированный эксперимент и опубликовать в локальном отчёте любой исход.
15. После каждого меняющего службы шага подтвердить восстановление P4, работоспособность служб, отсутствие временных drop-in/каталогов. Неудачные/оборванные результаты сохранить и отметить failed; не исправлять строки результатов задним числом.
16. Выполнить анализ только новых датированных серий, с обязательным F, семейной поправкой и единственным заранее предусмотренным добором. Не использовать `--conditional` как замену отсутствующим измерениям. Сохранить таблицы выбора, чувствительности и прямых контрастов, указав источники каждой серии.
17. Выгрузить новые результаты на Windows, сверить SHA256 и заполнить самостоятельный отчёт этапа 3 с фактическими датами, каталогами, параметрами, отклонениями и всеми несовпадениями с ожиданиями E1–E6.

## Разделение старых и новых данных

В архивном `results_v005` содержатся переименованные данные v004, что прямо указано в HANDOFF. В `reference/original-vm-results.tar.gz` находятся отдельные исходные данные существовавшей ВМ. Ни один из этих источников не является новым экспериментом этапа 3.

Новые измерения должны иметь новые датированные каталоги, свой manifest и однозначные источники для каждой таблицы. **Не смешивать старые архивные данные, прежние данные ВМ и новые измерения, не объединять их блоки, не выдавать старые числа за результат нового запуска.** Пересчёт прежних данных разрешён только как явно помеченный отдельный анализ, который не заменяет новые измерения.

На завершение этой передачи новые сырые измерения, функциональные исходы и статистические выводы этапа 3 отсутствуют. Стартовый комплект доступен агенту; препятствия к достоверному запуску перечислены выше.
