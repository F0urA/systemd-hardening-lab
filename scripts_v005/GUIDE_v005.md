# Как воспроизвести эксперимент (v005)

Эксперимент выполнен в два этапа: 11.10.2026 (шаги 1–12) и 12.10.2026 (шаги 13–18, дополнение `protocol_review_v005.txt`). Что получилось, какие были отклонения и находки, записано в `results_v005/report_v005.md` (в репозитории — `data/preliminary/report_v005.md`).

## Что нужно

- Чистая установка ALT Server 11.1 в виртуальной машине: 4 виртуальных процессора, около 4 ГБ памяти, доступ в интернет к репозиторию пакетов.
- Вход под root.
- Для нагрузочных серий — хост, на котором машина не переезжает между ядрами разного типа и не уходит в режим ожидания. На ноутбуке с гибридным процессором машина была привязана к производительным ядрам (маска задаётся процессу `VBoxSVC`, машина наследует её при запуске).

## Этап 1

Каталоги `scripts_v005` и `stand_v005` копируются на стенд рядом друг с другом, например в `/root/v005`. Все команды выполняются из `scripts_v005`.

| Шаг | Команда | Меняет службы | Результат в `/root/systemd-lab-results` |
|---|---|---|---|

| 2. Кандидаты | `./make_candidates_v005.sh`, `./make_ablation_v005.sh` | нет | `P6.conf`, `P1r.conf`, `P1c.conf`, `P4s.conf`, `P4n.conf` в каталогах профилей |
| 3. Микропроверки | `./probe_all_v005.sh` | нет | `probe-v005/<дата>` |
| 4. Соответствие модельного процесса реальному | `./context_compare_v005.sh` | да | `context-v005/<дата>` |

Скрипты, меняющие службы, требуют исходного состояния стенда (три службы под сохранённым P4, других drop-in нет) и возвращают его при выходе.

После перезагрузки машины процессы-мишени нужно запустить вручную:

```
for u in labweb labredis labpg root; do systemctl start lab-proc-target@$u; done
```

На этапе 1 сценарии шага 7 выполнялись первой редакцией скрипта: без усиленной проверки G1 и без ячеек уровня процесса (`docs/history/v003/scripts_v003/scenarios_v003.sh` — состояние тега `v003` прежней истории репозитория, коммит `f49be6b`).

### Шаг 5. Условие запуска серий

Серии запускаются, только если коэффициент вариации P0 в пилоте не выше 5 %. В `run.log` значение `CPU_PCT` должно быть выше 90: это признак того, что узкое место — сервер.

### Шаг 9. Нагрузочные серии

```
NGINX_N=100000 ./benchmark_v005.sh nginx 20 P4 P5 P6
REDIS_THREADS=3 REDIS_N=3000000 ./benchmark_v005.sh redis 20
PG_T=60 ./benchmark_v005.sh postgresql 10
```

В конце каждой серии печатается проверка для каждого кандидата: `PRIMARY_NONINFERIORITY_95` и `CPU_PER_OP_ONE_SIDED_95_UPPER_INCREASE`. Строка `INVALID MEASUREMENTS REPEATED` показывает, сколько измерений повторено из-за пауз виртуальной машины.

### Шаг 10. Причина роста затрат

```
NGINX_N=100000 ./benchmark_v005.sh nginx 20 P4 P4s P4n
python3 ablation_report_v005.py <каталог серии>/results.csv
```

## Этап 3 (дополнение `protocol_review2_v005.txt`, рецензия на v004)

### Повторение этапа 3 с нуля одной очередью

Добавлено после эксперимента. Измерения этапа 3 выполнялись очередью драйверов, часть которых
привязана к тому запуску (возобновление после сбоя, сверка его архивов), а драйверы первого запуска не
сохранились. `orchestration_v005/run_stage3.sh` собирает ту же очередь заново: те же скрипты измерений,
параметры, профили и порядок (`data/main/protocol/RUN_PROTOCOL.md` и дополнения к нему). Опубликованные данные
получены не им. На чистой ВМ ALT Server 11.1 (4 vCPU, 4 ГБ, доступ к репозиторию пакетов), под root:

```
git clone https://github.com/F0urA/systemd-hardening-lab.git /root/src
bash /root/src/scripts_v005/orchestration_v005/deploy_stage3.sh
B=/root/systemd-hardening-lab
bash $B/run_stage3.sh stand       # сборка стенда, сверка профилей и помощников с исполнявшимися
bash $B/run_stage3.sh preflight   # контракт, контексты, цели, микропроверки (около 20 мин)
bash $B/run_stage3.sh primary     # пилот, R1, R2, R3, R5, пилоты R4 и R4 (около 8 ч)
bash $B/run_stage3.sh post        # первый анализ, добор, окончательный анализ, CAP, монтирование, memcached
bash $B/run_stage3.sh seal        # манифест SHA256 и один архив results_v005
```

Клон не должен лежать внутри `SLAB_BASE` (по умолчанию `/root/systemd-hardening-lab`). Каждую фазу можно
запустить только один раз; результаты не перезаписываются. На время нагрузочных фаз на хосте запускается
`host_v005/host-monitor-v005.ps1`. Сборщики `host_v005/collect_results*_v005.ps1` узнают только контроллеры
исполнявшегося запуска, поэтому новый запуск закрывается фазой `seal` и копируется одним архивом
`$B/results_v005-closed.tar.gz` (рядом его SHA256). На хосте его распаковывают в короткий путь (на Windows
длинные имена каталогов матрицы монтирования упираются в предел 260 символов) и сверяют:
`python verify_raw_v005.py results_v005 results_v005/SHA256-CLOSED-RESULTS.txt`. Отличия от исполнявшейся очереди перечислены в начале `run_stage3.sh`:
один пилот вместо двух, цели и абляция capabilities измеряются сразу исправленными редакциями, порт 55432
резервируется для всех серий PostgreSQL. Без ВМ очередь проверяется `tests_v005/test_run_stage3.py`:
заглушки повторяют опубликованные серии, и неизменённый `analyze_v005.py` принимает журнал очереди и выдаёт
тот же план добора, что в исполнявшемся запуске.

## Таблица критериев и выбор

Уровень решения с поправкой на число кандидатов и плановый добор (замечания 9, 10):

```
R=/root/systemd-lab-results
python3 build_criteria_v005.py --probe $R/probe-v005/<дата> --scenarios $R/scenarios-v005/<дата> \
  --bench nginx=$R/nginx/benchmark-v005/<общая серия>:P1c,P4,P5,P6 \
  --bench nginx=$R/nginx/benchmark-v005/<серия P1/P2/P1r>:P1,P2,P1r \
  --bench redis=$R/redis/benchmark-v005/<дата> \
  --bench postgresql=$R/postgresql/benchmark-v005/<дата> \
  --level 0.05 --family nginx=4 --family redis=4 --family postgresql=4 --looks 2 --out $R/criteria.csv
# цель-добор серии кандидата с исходом NEEDS_MORE_DATA: повторить серию и объединить
#   --bench nginx=<серия1>+<серия2>:<кандидат>
python3 select_profile_v005.py $R/criteria.csv --budgets 2,5,10,15 \
  --require nginx=G2-read-app-secret   # пример обязательной цели (замечание 5)
python3 order_sensitivity_v005.py $R/criteria.csv --budgets 2,5,10,15   # замечание 16
```

Источник границ для каждого кандидата задаётся в командной строке.

## Дополнительные расчёты

- `robustness_v005.py` — три статуса кандидата, граница с поправкой Бонферрони, бутстреп-границы, наименьший порог допуска; `--pairs A-B` — прямые парные контрасты между защищающими профилями одной серии.
- `pool_series_v005.py` — объединяет две серии в один файл с последовательными номерами блоков (расчёт по 40 блокам).
- `freq_adjust_v005.py` — расчёт с нормировкой на частоту процессора хоста; нужен журнал состояния хоста и время окончания измерений. Для серий 11.10.2026 разведочный, для серии этапа 2 заявлен в протоколе заранее.
