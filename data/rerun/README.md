## Почему memcached измерен отдельно

1. `install_memcached` в `run_stage3.sh` 6eb755e сравнивал версию из `apt-get -s` целиком:
   `1.6.42-alt1:p11+418735.100.1.1@1779279920` ≠ `1.6.42-alt1`, хотя пакет тот же. В дополнении
   сравнивается часть до `:`.
2. `memcached_stage3_v005.sh` принимает версию только по шаблону `[a-zA-Z0-9.-]`, а `memcached -V` на ALT
   печатает `1.6.42_alt1`. В попытке 2 скрипт запущен из копии `memcached/frozen-memcached-addendum` с `_` в
   обоих шаблонах; других изменений нет (`memcached/results_v005/driver/addendum2-memcached-stage3.diff`;
   `reproduce.py` проверяет, что остальные 108 файлов копии совпадают с разложенными). Пакет повторно не
   ставился.

Остальное — `phase_memcached` из `run_stage3.sh` без изменений. Обе ошибки и неработающие после снапшота
мишени исправлены в `run_stage3.sh` после повтора. Опечатанные результаты основного прогона не тронуты:
файлы каждой попытки перечислены в своём манифесте (`SHA256-ADDENDUM-MEMCACHED.txt`,
`SHA256-ADDENDUM2-MEMCACHED.txt`) и лежат в своём архиве.

## Известные особенности

Разобраны после эксперимента; записи эксперимента и его выводы по протоколу не меняются.

**Отказ P1 memcached по истечению срока.** Часы memcached обновляются раз в секунду, ключ с временем
жизни 2 с исчезает через 1–2 с, и ожидание 3,2 с оставляет запас около 1,2 с. По журналу unit этой проверки
(`memcached/results_v005/memcached/functional-v005/20261020T032607Z-137386/journal.txt`) часть контракта до
перезапуска заняла у P1 7,0 с против 4,4–5,3 с у P0, P2, P4, P6, а перезапуск после неё — 5,1 с против
0,0–1,2 с: в эти секунды ВМ, по-видимому, приостанавливалась. Директивы P1 к часам не относятся.

Диагностика по `scripts_v005/protocol_memcached_ttl.md` (протокол на GitHub в коммите `7d15f51` до запуска)
выполнена 24.10.2026 на той же ВМ (`memcached-ttl-diagnostic/`): 150 проверок, по 30 на P0, P1, P2, P4, P6.
Отказов проверки `expiration` нет ни у одного профиля, у P1 — 0 из 30; остальная часть контракта до
перезапуска тоже прошла везде. Паузы метрономов не короче 1000 мс были в 9 проверках (до 10,3 с). В 136
проверках без пауз ключ исчез через 1,07–2,04 с, кроме трёх, где он исчез раньше: 0,36 и 0,63 с (P0) и
0,74 с (P6). Время исчезновения больше 2,3 с встретилось только при паузах: 6,69 с у P6 при паузе 8,45 с,
то есть во время паузы ключ пережил бы ожидание 3,2 с. Исход по правилам протокола — `UNCLASSIFIED`:
условие `NOT_REPRODUCED` не выполнено из-за трёх ранних исчезновений, предсказанное окно 0,9–2,3 с
оказалось неверным снизу. Систематического эффекта P1 нет (условие `PROFILE_EFFECT` далеко не выполнено),
отказ 20.10 не воспроизвёлся; его причина по-прежнему не установлена, и косвенным признаком паузы остаётся
журнал той проверки. P1 остаётся исключённым.

**Измерения, повторённые из-за паузы ВМ** (`derived/stall_sensitivity.txt`, `stall_sensitivity.py`).
Измерение с паузой метронома длиннее 500 мс по протоколу недействительно и повторяется; в расчёт входит
принятое повторение. Повторено: Nginx — 52 из 772 попыток (6,7 %), Redis — 1 из 121, PostgreSQL — 36 из 156
(23,1 %; P0 — 9, P1 — 4, P2 — 6, P1d — 6, P4 — 7, P6 — 4). Если вместо принятых повторений взять первые
попытки, исходы Nginx и Redis не меняются, а у PostgreSQL нижняя граница P6 падает с +8,3 до −8,1, и
неухудшение P6 не подтверждается. Допуск P6 PostgreSQL, а с ним и выбор P6, поэтому зависит от правила повтора.

**PostgreSQL на этом стенде не нагружает процессор.** Загрузка службы 31–50 %, затраты процессорного времени
на транзакцию почти постоянны (у P0 коэффициент вариации 1,1 %, у всех профилей 484–489 мкс), а пропускная
способность меняется вместе с загрузкой (r = 0,994; у P0 коэффициент вариации 10 %). Пропускную способность
определяет не процессор, а ожидание вне службы; профили по ней на этой точности не различаются. В первом
прогоне (`../derived/stall_sensitivity.txt`) загрузка в среднем 72 %, повторено 4 из 104 попыток.
