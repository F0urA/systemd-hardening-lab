ЭТАП 26: ПРЕДВАРИТЕЛЬНЫЕ ПАРАМЕТРЫ ПРИМЕНЕНИЯ ПРОЦЕДУРЫ v005 К MEMCACHED

Этот дополнительный протокол фиксируется вместе с кодом ДО создания профилей,
функциональных наблюдений и нагрузочных измерений memcached. Исходная процедура
procedure_v005.txt, структура допуска/выбора и статистические пороги не меняются.
Файлы старых редакций и старые результаты служат только справочным материалом.

1. СЛУЖБА И ГРАНИЦЫ
Из очереди memcached / unbound / mosquitto выбрана первая доступная memcached;
apt-cache существующей ALT Server 11.1 показал 1.6.42-alt1. Установку пакета
выполняет оператор. Точная версия бинарного файла сохраняется режимом register
до эксперимента и затем должна совпадать с ответом VERSION по TCP.

Отдельный unit: slab-memcached-v005.service. Отдельный системный пользователь:
labmemcachev005, без login-shell и членства в административных группах.
Параметры процесса: -l 127.0.0.1 -p 11212 -U 0 -m 64 -t 1 -B ascii.
TCP только на loopback; UDP выключен; дополнительные public listeners, extstore,
proxy configuration, persistent files и журналы данных не включаются.
Штатный memcached.service не изменяется. При подготовке имена пользователя,
unit, каталогов профилей и порта обязаны быть свободны.

2. ЦЕЛИ И КАНДИДАТЫ, ЗАДАННЫЕ ДО ДАННЫХ
Рабочая конфигурация этого in-memory daemon не ссылается на постоянные пути
данных/конфигурации, читаемые или записываемые службой. Каталоги регистрации,
сценариев и результатов принадлежат оператору и не являются путями данных
memcached. По правилу вывода файловых целей процедуры получается G=пустое
множество; обязательные цели также пусты. Не придумываются файл-секрет, каталог
данных или ложные сценарии файловой защиты. Для всех кандидатов g(D)=s(D)=0
по определению пустого множества; это ограничение переносимости процедуры.

Успешные неаутентифицированные SET/GET/delete с loopback видны в контракте:
это диагностическое наблюдение об интерфейсе сервера, не цель G и не доказательство
защитного эффекта systemd. Сетевая порча/чтение значений не включается задним
числом в g(D). Никакой атаки на другие службы или интернет не проводится.

Проверяется конечное множество P0, P1, P2, P4, P6. P0 — тот же unit/User/порт/
CPUAffinity, но без дополнительного drop-in. Четыре разных ограниченных
кандидата (M=4) выбраны заранее; утверждения о полном переборе hardening нет.
P1: PrivateTmp, ProtectHome, ProtectSystem=full, NoNewPrivileges.
P2: P1 + PrivateDevices, ProtectKernelTunables/Modules/Logs.
P4: P2 + ProtectControlGroups, ProtectProc=invisible, PrivateMounts,
RestrictNamespaces, RestrictAddressFamilies=AF_UNIX AF_INET, пустой
CapabilityBoundingSet, SystemCallFilter=~@mount @reboot @swap @module @raw-io
@debug, SystemCallErrorNumber=EPERM, MemoryDenyWriteExecute, LockPersonality,
RestrictRealtime, RestrictSUIDSGID.
P6: P4 + ProtectSystem=strict. Inventory постоянных записываемых путей пуст;
ReadWritePaths не добавляется. ReadOnlyPaths для выдуманных путей и P1d не
строятся. Неудачный профиль сохраняется как неработоспособный; параметры не
ослабляются по результатам. ЯВНОЕ ПРЕДВАРИТЕЛЬНОЕ ОТКЛОНЕНИЕ: требуемый разделом 2
procedure_v005.txt один шаг минимального ослабления для F=0 кандидата здесь не
реализован. Не изобретается заранее не подтверждённый причиной отказа кандидат.
При таком исходе этап является частичным применением процедуры, не полным
подтверждением её переноса; в результатах создаётся F_RELAXATION_NOT_IMPLEMENTED.txt.
Если все ограниченные кандидаты проходят F, это условное ограничение не активируется.
Любая дальнейшая редакция — отдельное отклонение
после знакомства с данными, а не исправление этого протокола задним числом.

3. ОБЯЗАТЕЛЬНЫЙ КОНТРАКТ F
Для каждого P0/P1/P2/P4/P6 после запуска выполняются точные проверки:
  version: ответ VERSION равен версии бинарного файла в регистрации;
  set: синтетический ключ записан с точным подтверждением STORED;
  get: возвращены точный key/flags/length, известные байты значения и END;
  delete: ответ DELETED, после чего GET этого ключа пуст;
  expiration: TTL=2 секунды, значение подтверждено сразу после SET;
              после заранее заданного ожидания 3,2 секунды значение отсутствует;
  restart: значение специального ключа подтверждено до systemctl restart;
           после успешного restart и готовности сервера ключ отсутствует.
Потеря значения при restart ожидается для этой in-memory конфигурации и является
PASS, не ошибкой сохранности. Предварительная проверка restart-value-prepared
обязательна как доказательство предпосылки; отсутствие ключа до restart не может
засчитываться как успешная проверка потери значения.
Любой FAIL/ERROR или отсутствие обязательного наблюдения даёт F=0. Сохраняются
операционный functional.csv, summary contract.csv, числовой F.csv, candidates.csv
и сырые JSON. Пустой goals.csv имеет только заголовок, соответствует G=пусто.
Результаты всех кандидатов сообщаются, включая отсутствие допустимого кандидата.

Клиент использует классический текстовый протокол memcached. Формат команд,
ответов и относительное истечение срока проверены по первичной документации:
https://github.com/memcached/memcached/blob/master/doc/protocol.txt
Выбранное ожидание 3,2 секунды учитывает секундную гранулярность TTL; после данных
его не меняют. Заголовки, значения, отсутствие ключа и ошибки проверяются явно.

4. Emicro И ДИАГНОСТИКА
Emicro реально измеряется теми же 32 основными и 4 расширенными пробами v005,
через установленные isolation_probe.py, extended_probe.py, slab_fp_v005.sh и
slab_inservice_v005.sh. Существующие несовпадающие помощники не перезаписываются.
Создаётся только отдельный экземпляр lab-proc-target@labmemcachev005 как same-UID
мишень. Собственный launcher читает профиль в пары systemd-run -p и задаёт тот же
User/Group/CPUAffinity; общий svc_user не изменяется. P0 использует тот же launcher.

Для каждого memcached__P0/P1/P2/P4/P6 должны присутствовать все 36 уникальных
статусов, без ERROR. P0 должен иметь хотя бы одну ALLOWED пробу. Пустой/частичный
baseline или ошибка не заменяются диагностическим нулём. Неверная серия проб
помечается failed; сырые outputs остаются. Затем metric_summary_v005.py считает
обычный baseline-calibrated Emicro36 без нового правила. N/A сохраняется как N/A,
не превращается в подтверждённое блокирование.
Это модельные процессные пробы, а не исполнение внутри native memcached.
Fingerprint и mount-table реального процесса дополнительно сохраняются;
равенство native и model contexts не объявляется без отдельной сверки.
Exposure измеряется systemd-analyze security, число директив — по сохранённым
профилям. Если диагностические данные неполны, ограничение сообщается явно.

5. НАГРУЗКА, РАНДОМИЗАЦИЯ И ДЕЙСТВИТЕЛЬНОСТЬ
Основной X: GET/сек. Одно синтетическое значение 128 байт, один заранее заданный
ключ, флаги=0, без expiration. Seed и прогрев выполняются ДО отсчёта CPU/wall.
Прогрев: 5000 GET. Измерение: ровно 3000000 GET с подтверждением всех ответов.
Клиент: Python stdlib, 50 постоянных TCP-соединений, 3 client threads с 17/17/16
соединениями. На каждой активной связи фиксированный pipeline=32: отправляется
один ограниченный batch всем связям потока, затем точно проверяются все ответы.
TCP_NODELAY включён, socket timeout=10 секунд. Нельзя менять pipeline/байты/
соединения по увиденной эффективности профилей.

20 randomized paired blocks. В каждом P0 и все F=1 ограниченные кандидаты,
одинаковые параметры/прогрев, restart перед измерением. Randomization seed
создаётся при register и сохраняется до профилей; shuffle определяется seed и
номером блока. Сервер закреплён за vCPU0; все потоки клиента — taskset 1-3.
CPUAccounting измеряет всю службу, а не генератор. CPU/wall охватывают запуск
Python load и обработку GET; setup, seed и warmup вынесены перед отсчётом.
Сохраняются cpu_pct, cpu_us_per_op, ops, wall_ns и raw JSON каждого attempt.
Elapsed clock заранее определён как CLOCK_MONOTONIC_RAW: runner start/end,
client elapsed и heartbeat измеряют Linux RAW-clock в наносекундах. UTC/wall
используется только для имён/меток/journal, не длительности или отбраковки пауз.
Это фиксируется до данных memcached после выявленного chrony slew в предыдущей
серии другой службы; предшествующие clock-invalid серии не становятся валидными
от этого исправления и не входят в новые измерения.

На vCPU0 и client CPUs работают независимые 20-ms heartbeat detectors.
При max_gap_ms>500 замер записывается в invalid.csv и повторяется немедленно,
до 5 попыток; raw JSON и оба heartbeat сохраняются для каждой попытки.
Ошибка GET/неполный ответ/неверные байты обрывает серию и сохраняется как failed;
успешными неполные серии не объявляются. Паузы не исправляются в исходных данных.
CPU saturation сообщается как диагностика режима, не постфактум подобранное
условие отбраковки этой новой службы.

6. АНАЛИЗ ПО НЕИЗМЕННОЙ ПРОЦЕДУРЕ
delta=5%; H=2,5,10,15%; family level=0,05; M=4, K=2 заранее, alpha=0,00625.
При NEEDS_MORE_DATA разрешён только один плановый добор ещё 20 блоков с теми же
параметрами. Второй look использует следующие 20 номеров в seed-shuffle; blocks
в CSV снова 1..20 для стандартного pooling. Второго добора нет. После предела
любой INCONCLUSIVE остаётся незавершённым выводом, не подгоняется под выбор.
M не сокращается после исключения F=0 кандидатов. Старые серии не объединяются
с новыми. Обязательный contract.csv передаётся build_criteria явно.
G=пусто не доказывает равенство безопасности кандидатов: критерий целей здесь
не различает их. Выбор, если он возможен, определяется допуском и диагностической
политикой s,Emicro,Exposure,n; вывод о превосходстве B над A+ не заявляется.

7. ПОРЯДОК РЕЖИМОВ И СЛЕДЫ
Оператор сначала устанавливает memcached и обеспечивает обычный v005 foundation
с lab-target/uid-helper/template и синтетическими объектами 36 проб.
Новый runner не устанавливает пакеты и не запускает старый setup_stand.

  ./memcached_stage3_v005.sh register
    -> REG_DIR: parameters.json (включая seed и actual version), code.sha256,
       platform.txt, target-unit.txt, registration.sha256; ещё нет user/profiles.
  ./memcached_stage3_v005.sh prepare REG_DIR
    -> после проверки хешей создаёт только scoped user/unit/profiles/target;
       сохраняет отдельный prepare-log и приводит службу к P4.
  ./memcached_stage3_v005.sh check REG_DIR
    -> функциональные результаты; запомнить CONTRACT_DIR.
  ./memcached_stage3_v005.sh probe REG_DIR
    -> PROBE_DIR с реальными 36 пробами и metrics.csv.
  ./memcached_stage3_v005.sh measure REG_DIR CONTRACT_DIR 1
    -> BENCH_DIR с compatible results.csv и raw attempts.
  ./memcached_stage3_v005.sh measure REG_DIR CONTRACT_DIR 2
    -> только если нужен предусмотренный добор после первого завершённого look.
  ./memcached_stage3_v005.sh cleanup REG_DIR
    -> возвращает только owned memcached unit под сохранённый P4, не меняет
       nginx/redis/postgresql и не удаляет данные/пользователя/результаты.

ROOT=${SLAB_RESULTS_ROOT:-/root/article-experiment/20261012-v005/results_v005};
TZ=UTC. Старый /root/systemd-lab-results не изменяется. Серию memcached нельзя
проводить параллельно другим нагрузочным сериям. Каждый результат содержит
регистрацию, журналы, SHA256 и FAILED.txt при аварии. sha256-all.txt покрывает

Финальный hash этого журнала и всего каталога фиксирует родитель после завершения
процесса; это не скрывается и не выдаётся за hash незакрытого потока.
Freeze делается отдельным пакетом до prepare/наблюдений. Локальная фиксация
хешей не выдаётся за независимую публичную preregistration: GitHub не изменяется.
Ни SSH-настройки, ни root passwords/private SSH keys в эти материалы не включены.
