ПРОТОКОЛ v003

Имена скриптов и каталогов в этом тексте приведены к единой нумерации v005 при переходе к
редакции v005 (прежде - к v004 при переходе к редакции v004); содержание не менялось.
Текст на момент фиксации - в истории репозитория (тег v003).

Методика многокритериального выбора профиля hardening системных служб Linux средствами systemd
Проверка на трёх задачах выбора: Nginx, Redis, PostgreSQL

Протокол фиксируется коммитом в открытый репозиторий ДО запуска scenarios_v005.sh
и functional_ext_v005.sh. Время коммита должно быть раньше времени в журналах
этих запусков. Черновики протокола из каталога scripts_v002 не фиксировались и
силы не имеют.

1. СТЕНД
Стенд собран заново на чистой установке ALT Server 11.1 скриптом
setup_stand_v005.sh из файлов каталога stand_v005 (unit-файлы, конфигурации,
профили P1-P5 и программы проверок взяты из приложений предыдущей версии статьи).
Описание стенда с версиями и контрольными суммами: results_v005/stand-v005.txt.
Виртуальная машина VirtualBox 7.2.12: 4 виртуальных процессора, 3,9 ГиБ памяти.
Хост: ноутбук, Intel Core Ultra 9 285H (6 производительных и 10 энергоэффективных
ядер), 31,5 ГБ памяти, Windows 11.
Это другой стенд, чем в предыдущей версии статьи; результаты двух стендов не
объединяются.

Известны автору результаты прежнего стенда (предыдущая версия статьи).

3. ПАРАМЕТРЫ, ЗАДАВАЕМЫЕ ОПЕРАТОРОМ
Функциональный контракт F: служба запускается и проходит проверку svc_health
(Nginx: HTTP 200 и эталонное тело; Redis: PING; PostgreSQL: pg_isready).
Порог неухудшения: delta = 5 %. Показатель: RPS (Nginx, Redis), TPS (PostgreSQL);
большее значение лучше.
Стоимость: процессорное время службы на одну операцию. Сетка бюджетов
H = 2, 5, 10, 15 % прироста относительно P0.
Цели нарушителя G: раздел 5.

4. КАНДИДАТЫ
Nginx:      P0, P4, P5 (P4 + ReadOnlyPaths для web-каталога), P6.
Redis:      P0, P4, P6.
PostgreSQL: P0, P4, P6.
P6 = сохранённый P4 + ProtectSystem=strict + ReadWritePaths=<пути записи службы>;
построен скриптом make_candidates_v005.sh и после этого не правился:
  Nginx       ReadWritePaths=/run -/var/log/slab-nginx-error.log
              и пять каталогов -/var/spool/nginx/tmp/{client,fastcgi,proxy,scgi,uwsgi}
  Redis       ReadWritePaths=/var/lib/systemd-lab/redis
  PostgreSQL  ReadWritePaths=/var/lib/systemd-lab/postgresql
В пилоте все три P6 прошли функциональный контракт F. После фиксации файлы
профилей не правятся. Если кандидат откажет в основной серии, он исключается;
допускается один шаг минимального ослабления, оформляемый как новый кандидат P6a
с отдельной строкой в таблицах.

5. ЦЕЛИ НАРУШИТЕЛЯ И ПРАВИЛА ИСХОДА
Модель: нарушитель исполняет действия с правами процесса службы.
Nginx G1  подмена отдаваемого документа. Факторы: каталог принадлежит root /
          каталог принадлежит labweb; контекст worker (labweb) / master (root).
          ACHIEVED: запись удалась и HTTP отдаёт подменённое содержимое.
          BLOCKED:  запись не удалась и HTTP отдаёт исходное содержимое.
Nginx G2  чтение секрета приложения, доступного службе по её назначению.
Redis G1  запись файла вне каталога данных через сам сервер (CONFIG SET dir +
          SAVE). Каталог-цель принадлежит labredis / root. Если сервер по
          умолчанию отклоняет CONFIG SET dir, это записывается отдельной строкой,
          а сценарий выполняется с enable-protected-configs yes как модель
          сервера без этой защиты.
PostgreSQL G1  запись файла вне каталога данных через COPY ... TO.
               Каталог-цель принадлежит labpg / root.
PostgreSQL G2  запуск программы через COPY ... FROM PROGRAM.
Любой иной исход записывается как UNEXPECTED и разбирается отдельно; такие
строки не исправляются и не удаляются.

Число заблокированных целей профиля D:
    g(D) = число ячеек (цель x права x контекст), где исход в P0 = ACHIEVED,
           а в D = BLOCKED.
Ячейка, заблокированная уже в P0 обычными правами доступа, профилю не
засчитывается.

6. ОЖИДАНИЯ, ЗАПИСАННЫЕ ЗАРАНЕЕ
E1. Каталог root, контекст worker: BLOCKED во всех профилях, включая P0.
E2. Каталог root, контекст master: ACHIEVED в P0 и P4, BLOCKED в P5 и P6.
E3. Каталог labweb: ACHIEVED в P0 и P4 в обоих контекстах, BLOCKED в P5 и P6.
E4. Nginx G2 и PostgreSQL G2: ACHIEVED во всех функциональных профилях.
E5. Redis G1 и PostgreSQL G1, каталог службы: ACHIEVED в P0 и P4, BLOCKED в P6;
    каталог root: BLOCKED во всех профилях.
E6. Exposure у P4 и P5 одинаков; у P6 не выше, чем у P4.
Несовпадение с ожиданием сообщается как результат.

7. ИЗМЕРЕНИЯ ЭТОЙ СЕРИИ
Изоляция (выполнено до фиксации): 32 основные и 4 расширенные микропроверки,
один способ запуска для P0 и всех профилей. Основной показатель Emicro по 36
проверкам без исключений; операции, необходимые службе, перечисляются отдельно.
Для Nginx в правило выбора входит Emicro контекста рабочего процесса (labweb);
значение для главного процесса (root) приводится рядом.
Цели нарушителя: scenarios_v005.sh для трёх служб.
Расширенная функциональная проверка (functional_ext_v005.sh) под каждым
кандидатом; в контракт F не входит, приводится таблицей «операция x кандидат»:
  Nginx       переоткрытие журналов (USR1); reload с двумя рабочими процессами;
              ответ 404 на несуществующий документ
  Redis       BGSAVE; BGREWRITEAOF; сохранение значения после restart
  PostgreSQL  CHECKPOINT; reload; запрос с jit = on и jit_above_cost = 0
Отказ операции под кандидатом записывается как результат.

8. НАГРУЗОЧНЫЕ СЕРИИ: НЕ ВХОДЯТ В ЭТУ СЕРИЮ
Пилот на данном хосте показал, что производительность одного и того же режима
меняется на десятки процентов: Windows переносит виртуальную машину между ядрами
разного типа, закрепить её за производительными ядрами не удалось. Порог в 5 %
при таком разбросе проверить нельзя, поэтому серии benchmark_v005.sh и опыт о
причине роста затрат (make_ablation_v005.sh, ablation_report_v005.py) на этом
хосте не выполняются. Данные пилота в анализ не входят и сохраняются только как
обоснование этого решения. Серии выполняются на другом хосте; их параметры
фиксируются отдельным дополнением к протоколу до запуска. План анализа:
  d_i = X(D,i) - 0,95 * X(P0,i); L95 - односторонняя нижняя 95 %-я t-граница
  среднего d; условие L95 > 0.
  r_i = c(D,i) / c(P0,i), c - процессорное время на операцию; U95 - односторонняя
  верхняя 95 %-я t-граница среднего ln r в процентах прироста; условие U95 <= H.
  Блоки из первичного анализа не исключаются.

9. ПРАВИЛА ВЫБОРА
Правило A (сравнение): F = 1; минимум Exposure; при равенстве меньше директив.
Правило B (предлагаемое): допустимы кандидаты с F = 1, L95 > 0 и U95 <= H;
среди них последовательно: максимум g(D); максимум Emicro; минимум Exposure;
меньше директив. Оставшееся равенство сообщается как равенство.
Пока нагрузочных данных нового стенда нет, условия L95 > 0 и U95 <= H не
проверены. Правило B в этой серии применяется условно: сообщается, какой
профиль был бы выбран среди кандидатов с F = 1, если все они пройдут допуск по
производительности и стоимости, и это условие называется в тексте прямо.

10. ОТЧЁТНОСТЬ
Для каждой службы приводится таблица «кандидат x критерии» и выбор по A и
условный выбор по B. Сообщаются все три задачи, в том числе те, где правила дали
один и тот же профиль. Вывод о превосходстве правила B не делается; предмет
вывода - в каких условиях правила расходятся и по какому критерию.
