# v005: первый анализ и единственный добор

Это локальная проверка оркестрации до завершения primary. Реальные нагрузочные
данные при подготовке этих изменений не анализировались; доступ к ВМ не
использовался. Frozen/core/memcached/mount-state файлы не изменялись.

## Границы анализа

- Первый анализ требует `driver/primary-corrected-finished.txt`, корректного
  журнала `primary-corrected-ledger.csv` и конечного `R4-condition.txt`.
  Само наличие `results.csv` или `RESULT_DIR` не доказывает завершённость.
- Принимаются только новые каталоги под
  `/root/article-experiment/20261012-v005/results_v005/<service>/benchmark-v005/`.
  Проверяются точные параметры исправленного таймера `CLOCK_MONOTONIC_RAW`,
  полный набор профилей/блоков, уникальность порядков, допустимые принятые
  измерения, контрольная сумма CSV и отметки завершения/восстановления P4.
  Частичные попытки и старые timing-invalid серии никогда не объединяются.
- AB: каждый из двух клиентов должен подтвердить `NGINX_N` в `Complete
  requests`; `Failed requests` и, при наличии, `Non-2xx responses` сверяются с
  CSV. PG: `number of transactions actually processed` сверяется с `ops`,
  напечатанный failed count — с `failed`; отсутствие failed count сохраняется
  как ограничение. Redis: присутствующий completed count сверяется с N/CSV,
  но режим `-q` может его не показывать. Тогда явно сохраняется
  `COUNTS_NOT_EXPOSED_BY_QUIET_OUTPUT`: заданный N, успешный producer exit и
  quiet summary не объявляются подтверждённым native completed count.
  Отчёты всех принятых `B<block>-<profile>-a<attempt>` и их SHA256 входят в аудит.
- Терминальный failed primary после одной технической retry получает
  `NO_VALID_PRIMARY`; остальные полные независимые серии сохраняются.
  Если полных серий нет вообще, сохраняются coverage и пустой plan,
  статистический selection не создаётся.
- Пропущенный этап, повторная строка, успешный этап с последующей retry,
  повторно использованный каталог или отсутствие конечной отметки — отказ
  от анализа, а не разрешение собрать несколько частичных запусков.

## Замороженный план и два look

`extension-plan.json` теперь имеет envelope `v005-first-look-plan-1`. Он
содержит только полные валидные primary серии, их каталоги и SHA256, SHA256
анализатора/неизменных статистических модулей и конечного журнала. SHA256
самого плана сохраняется в `analysis-first-look/plan-record.json`.

Правило не меняется: `level=0.05`, `K=2`; для combined Nginx `M=7`, Redis/PG
`M=5`, отдельного R4 `M=2`. Отдельные исходные Nginx-family views остаются
R1=4 и R5=3. Единственный прежний триггер добора — интервал throughput contrast
содержит ноль. Дополнительного CPU-триггера или новых численных outlier cuts нет.

Перед запуском extension driver вызывает режим структурной проверки
`--validate-extension-plan ... --emit-plan-tsv ...`: это не новый статистический
look. План нельзя пересоздать после начала добора. Атомарный каталог
`extension-claim-v005` не позволяет второму контроллеру запустить новую очередь.
Для каждого заранее указанного этапа разрешены только исходная попытка и одна
полная техническая retry при ошибке, с тем же множеством профилей и параметрами.
Остальные заранее запланированные этапы продолжаются после терминальной ошибки.
Успешная попытка дополнительно проверяется анализатором без вычисления новых
bounds. Пустой план тоже закрывает пустой ledger/finished marker — без нагрузок.

Final требует `extensions-finished.txt`, точного исполненного плана и
`extension-ledger.csv`. Для каждой строки plan проверяются ровно её профили
плюс P0, количество блоков, concurrency и уникальная новая серия. Failed
planned extension явно получает `NO_VALID_EXTENSION`, first-look bounds/status
не заменяются данными частичной попытки; третьего look или ещё одной очереди нет.

При любом таком ограничении combined результат называется
`combined-selection-INCOMPLETE_SCOPE.txt` и помечается условной неполной
диагностикой; обычный final `combined-selection.txt` не создаётся.
`primary-coverage.json`, `extension-coverage.json` и `analysis-status.json`
сохраняют причины и список затронутых этапов. Неполная/повреждённая очередь
даёт `validation-error.json` и ненулевой код; последовательная родительская
очередь вправе продолжать остальные независимые работы, но не новый добор.

## R4 и трудоёмкие описательные проверки

В неизменном primary driver lookup R4 pilot использует имя без `-retry`.
Если конечный R4 FAILED, анализатор отдельно проверяет сохранённую успешную
retry и сообщает, достигала ли она записанного диапазона CPU(P0). Это аудит
ошибки исполнителя, не новый выбор C и не ретроактивный запуск R4. FAILED при
подходящей retry не является доказательством отсутствия нужного диапазона.

Трудоёмкий `robustness_v005.py` запускается только при `--final`, как
descriptive view первичной R1, не влияет на сохранённый plan/selection.

## Размещение на ВМ и проверка

Родитель размещает копию `analyze_v005.py` в отдельном `BASE/post-analysis/`.
Там нужны `raw-vm` → реальные `BASE/results_v005` и `frozen-primary` →
неизменный primary пакет со статистическими модулями. Неизменный
`inspect_series_v005.py` допускается рядом с анализатором либо в `BASE`;
анализатор использует оба пути импорта. Копии и символьные ссылки должен
создать/проверить родитель, без смешивания с архивными результатами.

Существующий `driver_post_primary_v005.sh` прочитан, но не изменён. Его
first/final interface совместим: первый запуск создаёт план; extension driver
принимает его путь; `--final` закрывает анализ. Wrapper запускает эту часть
только после controller PID/finished marker и продолжает независимые этапы
после явно записанного терминального ограничения анализа.

`tests/test_analysis_v005.py` работает только с TemporaryDirectory и
синтетическими CSV/ledger/raw outputs. Проверяются неполные/повторные/wrong-profile
данные, отсутствие marker, retry-порядок, неизменность плана и исходников,
точный extension scope, terminal failures, M/K, отсутствие robustness на первом
look и отсутствие обычного combined selection в incomplete final. В тестах
оркестрации subprocess вывода подменены: это не проверка научного результата;
неизменная функция bounds отдельно вызывается на синтетических данных.

Локальный результат: 15 tests PASS; shell syntax и Python AST PASS. Frozen
audit module выдаёт ResourceWarning о своём существующем `open()` при импорте
тестов — его код не исправлялся и тесты проходят.
