### Находки

- **Исходы целей совпали с ожиданиями E1–E6**, строк `UNEXPECTED` нет.
- **Правила A и B расходятся во всех трёх задачах.** Правило A выбирает P4 для каждой службы. Правило B (условно) выбирает P5 для Nginx и P6 для Redis и PostgreSQL.
- **Exposure не различает P4, P5 и P6**: 2,8 для Nginx и 2,1 для Redis и PostgreSQL, хотя P6 переводит файловую систему в режим только для чтения.
- **Обычные права доступа против ограничений systemd.** Рабочий процесс Nginx не может подменить документ в каталоге root и без ограничений. Главный процесс под P4 может: в каталог root пишет напрямую, в каталог labweb — сменив идентификатор на labweb (CAP_SETUID остаётся у него по необходимости). Под P5 и P6 запись блокируется во всех четырёх сочетаниях.
- **Redis сам отклоняет `CONFIG SET dir`** в конфигурации по умолчанию; сценарий выполнен с `enable-protected-configs yes` как модель сервера без этой защиты.
- **Модельный процесс эквивалентен реальному**: все поля отпечатка совпали для P0 и P4 у четырёх контекстов, включая CapAmb и число фильтров (28). Таблицы монтирования отличаются двумя точками, в путях которых стоит имя самого unit. Проверки, запущенные внутри Nginx (главный и рабочий процесс) и внутри PostgreSQL, дали те же 36 статусов, что и модельные.
- **Способ запуска baseline не влияет**: `su` и `systemd-run` дали одинаковые статусы P0 для трёх пользователей (`probe-v004/.../baseline-su`).
- **Знаменатель для непривилегированного контекста — 16, а не 17**, как на прежнем стенде: здесь `kernel.unprivileged_userns_clone = 0`, и создание пользовательского пространства имён запрещено уже в P0. Для главного процесса Nginx числа совпали с прежними: 27 из 29.
- **Расширенные проверки io_uring и keyring остаются доступны под всеми профилями** (X3, X4). С ними Emicro = 14/18 = 0,778.
- **Число фильтров системных вызовов**: P0 — 0, только группа директив с фильтрами — 17, P4 без этой группы — 11, P4 — 28. То есть «остальные» директивы тоже ставят фильтры.
- **Проверка PostgreSQL с JIT неинформативна**: запрос выполняется, но JIT на стенде не используется (`jit_used=no`), поэтому совместимость JIT с `MemoryDenyWriteExecute` не проверена.
- **Расширенная функциональная проверка**: все операции проходят под всеми кандидатами. Под P4–P6 после переоткрытия журналов владелец файла остаётся root: главный процесс не может сменить владельца.

### Отклонения и замечания о качестве данных

1. **Разброс в сериях Nginx выше, чем в пилоте.** В пилоте коэффициент вариации P0 был 2,3 %, в основной серии — 9,6 %, в серии о причине роста затрат — 12,6 %. В отдельных измерениях сервер оставался загружен на 96 %, но процессорное время на запрос вырастало в полтора–два раза: виртуальный процессор сервера получал меньше физического времени, чем учитывала гостевая система. Вероятная причина — занятость производительных ядер хоста другими процессами. Блоки не исключались, как требует протокол; из-за этого интервалы для Nginx широкие.
2. **Вывод для Nginx от разброса не зависит по знаку:** точечные отношения 85–90 %, в пилоте с малым разбросом P4 давал 92,3 %. Порог 5 % не пройден ни в одном расчёте.
3. **Серии Redis и PostgreSQL от разброса не пострадали:** коэффициент вариации 0,9–2,5 %. Измерения там длиннее (около 15 и 60 секунд против 4–5 секунд у Nginx).
4. **В `benchmark_v004.sh` добавлены метрономы** и повтор измерения при паузе виртуальной машины. Причина — пауза около 4 секунд в одном измерении пилота.
5. **Параметры Redis изменены по итогам пилота** до фиксации дополнения: три потока генератора и 3 000 000 запросов, чтобы узким местом был сервер (загрузка 98 %).
6. **Шаблонные службы процессов-мишеней не запускаются сами после перезагрузки** (в unit-файле нет раздела установки); после перезапуска машины они запущены вручную. На нагрузочные серии это не влияет.
7. **Направление эффекта для Nginx P4 было известно до основной серии** из пилота; это записано в дополнении к протоколу.

### Источник разброса: частота процессора хоста

Запись состояния хоста показала:

- Во время измерений производительные ядра занимала только виртуальная машина; энергоэффективные ядра простаивали. Посторонней нагрузки не было.
- Частота занятых производительных ядер менялась от измерения к измерению: от 99 до 171 % номинальной при среднем 155 %.
- Корреляция частоты с пропускной способностью — от 0,78 до 0,98 по профилям.

То есть разброс создаёт сам процессор ноутбука, меняя частоту в режиме турбо, а не действия пользователя и не методика. Это объясняет, почему в медленных измерениях сервер оставался загружен на 96 %, а процессорное время на запрос росло.
