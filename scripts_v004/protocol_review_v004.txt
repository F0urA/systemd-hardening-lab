ТРЕТЬЕ ДОПОЛНЕНИЕ К ПРОТОКОЛУ: РЕДАКЦИЯ v004 ПО ЗАМЕЧАНИЯМ К РУКОПИСИ v003

Фиксируется коммитом в открытый репозиторий ДО запуска scenarios_v004.sh и нагрузочной
серии этого дополнения. Время коммита должно быть раньше времени в журналах этих запусков.
Состояние репозитория, по которому написана рукопись v003, отмечено тегом v003.

1. ПРИЧИНА И ЧТО ИЗВЕСТНО К МОМЕНТУ ФИКСАЦИИ
Критический разбор рукописи v003 указал, что профили P1 и P2 проходят функциональный
контракт Nginx, но в нагрузочных сериях не измерялись, поэтому исход «ни один кандидат с
ограничениями не допущен» относится только к P4, P5 и P6. Это дополнение расширяет множество
кандидатов Nginx и уточняет формулировку правила выбора.
Автору известны все результаты серий 11.10.2026 (results_v004/report_v004.md, части 1-3), в
том числе: P1 и P2 работоспособны, их Exposure 8,7 и 7,3, доли заблокированных микропроверок
0,333 и 0,389 (рабочий контекст); P4, P5, P6 теряют 10-15 % пропускной способности; группа
директив P4 без фильтров системных вызовов (P4n) даёт прирост затрат около 7 %.
На стенде ещё не наблюдались: производительность и стоимость P1, P2, P1r, P1c; исходы целей
нарушителя для этих профилей; исходы усиленной проверки цели G1 (раздел 3) для любого
профиля; ячейки уровня процесса для Redis и PostgreSQL; число системных вызовов на операцию.
Скрипты v004 до фиксации проверены только на данных серий 11.10.2026: build_criteria_v004.py
и select_profile_v004.py воспроизводят прежний выбор, freq_adjust_v004.py - прежний отчёт.

2. КАНДИДАТЫ
Nginx, добавлены:
  P1   первая ступень лестницы (файл профиля прежний).
  P2   вторая ступень лестницы (файл профиля прежний).
  P1r  P1 + ReadOnlyPaths=/var/lib/systemd-lab/nginx-www: директива, привязанная к пути,
       применена к самой лёгкой работоспособной ступени.
  P1c  P1r + CapabilityBoundingSet=CAP_NET_BIND_SERVICE CAP_SETUID CAP_SETGID: набор
       capabilities, полученный для P4 шагом минимального ослабления.
P1r и P1c строит make_candidates_v004.sh; после построения файлы не правятся. Кандидат, не
прошедший функциональный контракт, исключается и сообщается; шаг ослабления для него не
выполняется.
Множество кандидатов Nginx: P1, P2, P1r, P1c, P4, P5, P6 (и базовый P0).
Redis и PostgreSQL: без изменений (P4, P6 и базовый P0). Лестница для них не строилась;
это ограничение сообщается.

3. ЦЕЛИ НАРУШИТЕЛЯ, СЦЕНАРИИ И ИХ АГРЕГИРОВАНИЕ
Цели G - прежние (protocol_v004.txt, раздел 5). Каждая цель проверяется набором сценарных
ячеек S: ячейка = (цель, владелец каталога-цели, контекст). Изменения проверки:
  а) Усиленная проверка Nginx G1 в контексте главного процесса (root). Если прямая запись
     не удалась, модельный процесс дополнительно пробует то, что доступно процессу root
     против точки монтирования только для чтения: запись в тот же каталог по пути
     /proc/1/root/... и перемонтирование точки монтирования на запись в собственном
     пространстве монтирования (mount -o remount,rw,bind); затем, как прежде, запись после
     смены идентификатора на labweb. Сработавший способ записывается (via=...).
  б) Ячейки уровня процесса для Redis G1 и PostgreSQL G1: ту же запись вне каталога данных
     выполняет модельный процесс с правами и профилем службы, без участия сервера
     (контекст process). Ячейки через интерфейс сервера (CONFIG SET dir + SAVE; COPY ... TO)
     сохраняются (контекст server). Сценарий Redis через сервер, как прежде, выполняется с
     enable-protected-configs yes; то, что сервер в конфигурации по умолчанию отклоняет
     CONFIG SET dir, записывается отдельной строкой.
Профили: Nginx - P0, P1, P2, P1r, P1c, P4, P5, P6; Redis и PostgreSQL - P0, P4, P6.

Агрегирование (изменено по сравнению с protocol_v004.txt, раздел 5, где g - число ячеек):
  s(D) = число ячеек, в которых исход под P0 = ACHIEVED, а под D = BLOCKED;
  g(D) = число целей, у которых BLOCKED под D все ячейки, достижимые под P0.
Цель, заблокированная не во всех ячейках, в g не засчитывается и перечисляется как
остаточный риск. Ячейка, заблокированная уже под P0, не засчитывается никому.

Ожидания, записанные заранее:
E7.  P1, P2: исходы Nginx G1 как под P0 (каталог root / рабочий контекст - BLOCKED,
     остальные три ячейки - ACHIEVED).
E8.  P1r: каталог labweb / рабочий контекст - BLOCKED; обе ячейки главного процесса -
     ACHIEVED обходом (via=proc1root и/или remount), так как у процесса root остаются
     CAP_SYS_ADMIN и CAP_SYS_PTRACE.
E9.  P1c: все ячейки G1 - BLOCKED.
E10. P4: как в серии 11.10.2026; P5 и P6: все ячейки G1 - BLOCKED и при усиленной проверке.
E11. Redis G1 и PostgreSQL G1, контекст process: как контекст server (каталог службы -
     ACHIEVED под P0 и P4, BLOCKED под P6; каталог root - BLOCKED везде).
E12. Nginx G2 и PostgreSQL G2: ACHIEVED под всеми работоспособными профилями.
E13. Exposure у P1r равен Exposure у P1; у P1c - ниже, чем у P1r.
Несовпадение с ожиданием сообщается как результат; строки не исправляются.

4. ПРАВИЛО ВЫБОРА (ФОРМУЛИРОВКА v004)
Допустим кандидат с ограничениями D (D не равен P0), если F(D) = 1, L95(D) > 0 и
U95(D) <= H. Условия и их расчёт прежние.
Правило B: среди допустимых последовательно - максимум g(D); максимум s(D); максимум Emicro
(для Nginx - контекст рабочего процесса, значение главного приводится рядом); минимум
Exposure; меньше директив. Оставшееся равенство сообщается как равенство.
Если допустимых кандидатов с ограничениями нет, исход правила - «среди проверенных
кандидатов допустимого нет». P0 не является выбором правила; исход не толкуется как
рекомендация оставить службу без ограничений.
Правило A (сравнение, прежнее): F = 1; минимум Exposure; при равенстве меньше директив.
Правило A+ (сравнение, новое): те же допустимые кандидаты, что у правила B; минимум
Exposure; при равенстве меньше директив. Оно отделяет вклад условий допуска от вклада
критериев целей.
Изменены после знакомства с данными серий 11.10.2026: исход при отсутствии допустимых
кандидатов, разделение g и s, правило A+. Для сравнения сообщается и выбор по правилу B в
формулировке protocol_v004.txt (P0 - кандидат, первый критерий - число ячеек).

5. НАГРУЗОЧНАЯ СЕРИЯ
Одна серия: benchmark_v004.sh nginx 60 P1 P2 P1r P1c P4 (P0 добавляется скриптом).
Параметры нагрузки, закрепление процессоров и правило действительности измерения - как в
protocol_load_v004.txt, разделы 3 и 4 (NGINX_N=100000, KEEPALIVE=0, PIN=1, STALL_MS=500).
Машина привязана к производительным ядрам хоста тем же способом.
Число блоков - 60, задано заранее; серия не останавливается досрочно и не продлевается.
Серия, оборванная ошибками запросов, повторяется целиком; каталог оборванной серии
сохраняется с пометкой failed.
Обоснование числа блоков: в сериях 11.10.2026 полуширина односторонней границы контраста
составляла 5-6 % от X(P0) при 20 блоках и около 4 % при 40. При 60 блоках и том же разбросе
ожидается около 3,5 %: условие L95 > 0 при пороге 5 % достижимо только для кандидата с
истинной потерей не более 1-1,5 %. Поэтому для каждого кандидата сообщается один из трёх
статусов (раздел 6), а не только «допущен / не допущен».
P4 входит в серию как якорь для сопоставления с сериями 11.10.2026 и в выбор по этой
серии не входит.
Источник критериев допуска: P4, P5, P6 - первая серия 11.10.2026 (как прежде, основная);
P1, P2, P1r, P1c - серия этого дополнения. Redis и PostgreSQL - серии 11.10.2026.

6. АНАЛИЗ
Первичный, как прежде: d_i = X(D,i) - 0,95 * X(P0,i); L95 и U95d - нижняя и верхняя
односторонние 95 %-е t-границы среднего d; стоимость - U95 среднего ln отношения затрат на
операцию. Блоки не исключаются. Статус кандидата:
  неухудшение подтверждено          L95 > 0 (условие допуска);
  потеря больше порога подтверждена U95d < 0;
  вывод не сделан                   иначе.
Тот же статус сообщается для серий 11.10.2026.
Вторичный, заявлен заранее: во время серии host_activity_v004.ps1 записывает на хосте раз в
две секунды загрузку и относительную частоту логических процессоров. Для каждого измерения
вычисляется средняя относительная частота f занятых производительных ядер и нормированная
пропускная способность X* = X * 100 / f; контраст и границы считаются так же
(freq_adjust_v004.py). Для стоимости - затраты, умноженные на f. Вторичный расчёт
приводится рядом с первичным; выбор делается только по первичному. Расхождение статусов
сообщается, ни один не объявляется окончательным. Измерения по журналу хоста не
отбраковываются.

7. АНАЛИЗ ЧУВСТВИТЕЛЬНОСТИ (robustness_v004.py)
Для каждой серии: нижняя граница на уровне 0,05 / M, где M - число кандидатов с
ограничениями у службы (Nginx - 7, Redis и PostgreSQL - 2); процентильные бутстреп-границы
среднего контраста (20 000 повторных выборок блоков, фиксированное начальное значение);
наименьший порог, при котором L95 > 0. В правило выбора эти расчёты не входят.

8. ОПИСАТЕЛЬНЫЕ ИЗМЕРЕНИЯ
  а) probe_all_v004.sh для P1r и P1c (доля заблокированных микропроверок).
  б) functional_ext_v004.sh для всех кандидатов Nginx, включая новые; в контракт F не
     входит.
  в) syscall_count_v004.sh: число системных вызовов на операцию для трёх служб под P0 при
     нагрузке серий (strace -c). Служит только для обсуждения причины различия потерь между
     службами; причинный вывод по нему не делается.

9. ОТЧЁТНОСТЬ
Сообщаются все кандидаты и любой исход: если ни один новый кандидат не допущен; если
допущен кандидат с g = 0; если допущен кандидат, блокирующий G1, и вывод рукописи v003 для
Nginx меняется. Вывод о превосходстве правила B не делается.
